# Design: [ADVERSARIAL] 对抗验证门控 (双层触发: 前置分类 + 后置裁决词检测)

> **触发**: 用户拍板接入对抗验证, 明确要求"触发范围把控好, 担心范围小(漏网)"。
> **成本约束**: 用户已确认 token 预算——触发类强制 1-3 次/日 (+3~10%), 默认"只攻击"模式 (省 ~40%)。
> **遵循**: adversarial-review skill (攻击非确认/带数据/用户裁决); 门控哲学 (机器强制非自觉)。

## 一、范围设计: 解决"宽 vs 贵"的张力

**核心洞察**: 单一层触发无法兼顾——按用户问句触发会漏(freshness 案: "怎么判断的"机制问句, 中途变成"超前判延迟"裁决); 全量触发太贵。

**双层结构**:

| 层 | 时机 | 机制 | 覆盖 | 成本 |
|---|---|---|---|---|
| **L1 前置触发** | pre_llm_call | 用户问句命中**裁决请求类**模式 → 证据链强制 `[ADVERSARIAL]` | 明牌裁决请求 | 子 agent (8-25K) |
| **L2 后置检测** | transform_llm_output | 扫描我**输出文本**的裁决词 → 有裁决词但证据链无 `[ADVERSARIAL]` → footer 警告 | **机制问句中途转裁决**的漏网 (freshness 类) | 一行警告 (~50 token) |

L2 是"范围小"的保险丝: 即便 L1 模式没命中用户问句, 只要我的**结论里出现裁决语言**, 就暴露"该跑没跑"。

## 二、L1 前置触发类 (用户问句)

**裁决请求类** (问我要"是不是/行不行/选哪个"的结论):

```
根因 / 是不是.*bug / 有没有.*bug / 有没有.*问题
有效吗 / 是否有效 / 因子.*有效
选哪 / 哪个.*方案 / 方案.*选 / 要不要.*(改|换|废)
废弃 / 下线 / 新增.*(规范|规则|硬规则)
能.*上线 / 可以.*上线 / 没问题吧
```

**明确不触发** (控制成本):
- 机制解释类: "X 是怎么判断的/怎么算的" → 走 `[CONTRACT]` (便宜) 不走 ADVERSARIAL
- 数据状态类: "延迟/最新/正常吗/对么" → 已被 `[CONTRACT]` 覆盖
- 执行类: "帮我写/优化/跑一下" → 非结论

## 三、L2 后置裁决词 (扫描我的输出)

```
根因是 / 这是个?bug / 不是.?bug / 确认.*有效 / 因子.*有效
建议(采用|废弃|选择方案) / 可以上线 / 数据.*无问题
```

命中且证据链无 `[ADVERSARIAL]` → footer 追加:
`⚠️ 对抗验证缺失: 结论含裁决词但未跑对抗验证`

**已知误报容忍**: 设计讨论类回复偶含"根因是"会误标——可接受 (信息性警告非阻断), 宁宽勿漏。

## 四、[ADVERSARIAL] 标签规范

- 内容: `[ADVERSARIAL] verdict=UNSHAKEN|WEAKENED|DESTROYED · 攻击N条 · <一句话>`
- 锚点校验: 必须含 `verdict|UNSHAKEN|WEAKENED|DESTROYED|对抗` 之一 (防空写)
- 执行模式: **只攻击** (attack-only) — 砍防御子 agent, 主线程自己回应, 省 ~40%
- 跑法: `delegate_task(goal=攻击指令+结论+契约锚点, toolsets=["file","terminal"])`, 与 adversarial-review skill Phase 2 一致

| 文件 | 改动 |

## 六、验证

1. 正例: "根因是什么"→L1 触发; "这个因子有效吗"→触发; "选哪个方案"→触发
2. 负例: "延迟是怎么判断的"→只 CONTRACT 不 ADVERSARIAL; "帮我写函数"→都不触发
3. 完备性: 缺/空写/带 verdict 三档
4. L2: 输出含"根因是"且无 [ADVERSARIAL] → footer 警告; 有 → 不警告
5. 语法 + import 实测; 提示重启双进程
